## 地址栏敲下回车之后

21:47，你在地址栏敲下 `example.com` 回车，大约 100 毫秒后页面出现。这 100 毫秒里，笔记本做的事可以粗分成四类：

- 把 `example.com` 问成一台服务器的 IP 地址
- 和一个从没打过交道的服务器确认「两边现在都能收发」
- 把一页文本切成能在网线或空气里跑的比特
- 每到一台中间设备，就重新决定下一段往哪送

这四件事的变化速度差得很远：网页内容一天能改十次，网卡十年换一代，而中间那些设备换不换、走哪条路，你的浏览器完全不知道。**协议分层**（protocol layering）要解决的就是这件事——把通信切成若干层，每一层只解决一类问题，只使用下一层提供的服务，不关心下一层内部怎么做。

分层这个想法出现在 1974 年：Cerf 与 Kahn 描述跨网通信时，把「端到端要保证什么」与「每一段链路怎么走」拆成了两件事，这是分层的起点；1978 年 TCP 被拆成 TCP 与 IP 两个协议；1984 年 ISO 发布 OSI 七层参考模型。工程上真正跑起来的是 TCP/IP 的四层划分，下面按这四层讲。

## 四层各管一段

| 层 | 这一段要决定的事 | 这一层用的地址 | 常见协议 |
| --- | --- | --- | --- |
| 应用层 | 要哪一页、用什么格式交换 | 域名与 URL | HTTP、DNS |
| 传输层 | 哪个程序收、数据是否完整有序 | 端口号 | TCP、UDP |
| 网络层 | 从哪台机器到哪台机器，跨网段接力 | IP 地址 | IP |
| 链路层 | 紧挨着的两个设备之间怎么把比特交过去 | MAC 地址 | 以太网、WiFi |

## 一层套一层

发送方把上层交下来的整份内容当作**载荷**（payload），在前面加上本层的**首部**（header），再交给下一层；接收方从头开始逐层剥掉首部，把剩下的交给上层。这个过程叫**封装**（encapsulation），剥的过程叫解封装。

它的直接后果是：同一段字节在不同层里的名字和长度都不一样。下面是一条最小 HTTP 请求的原始内容，逐字写出来是这样（`\r\n` 是回车加换行，各占一个字节）：

```http
GET /index.html HTTP/1.1
Host: example.com
User-Agent: curl/8.4.0
Accept: */*

```

按下字节数逐行数一遍：

- 请求行 `GET /index.html HTTP/1.1` 连同行尾，$26$ 字节
- `Host: example.com` 连同行尾，$19$ 字节
- `User-Agent: curl/8.4.0` 连同行尾，$24$ 字节
- `Accept: */*` 连同行尾，$13$ 字节
- 结尾那个空行，$2$ 字节

合计 $26 + 19 + 24 + 13 + 2 = 84$ 字节，这就是应用层交给传输层的东西。传输层在前面加 $20$ 字节 TCP 首部（源端口、目的端口、序号等），变成 $104$ 字节；网络层再加 $20$ 字节 IP 首部（源地址、目的地址、生存时间等），变成 $124$ 字节；链路层再加 $14$ 字节以太网首部与 $4$ 字节帧尾校验，变成 $142$ 字节。真正上线路的是这 $142$ 字节：

$$20 + 20 + 14 + 4 = 58$$

也就是说，为了让 $84$ 字节的请求跑起来，线路上一共多花了 $58$ 字节，占实际流量的 $58 / 142 \approx 40.8\%$。请求越小，这个比例越难看。换成一条满载的响应，载荷 $1500$ 字节，帧长 $14 + 1500 + 4 = 1518$ 字节，同样的 $58$ 字节首部只占 $58 / 1518 \approx 3.8\%$。

## 动手数一遍

把下面这段存成 `req_size.py` 再 `python3 req_size.py`：

```python
req = (b"GET /index.html HTTP/1.1\r\n"
       b"Host: example.com\r\n"
       b"User-Agent: curl/8.4.0\r\n"
       b"Accept: */*\r\n"
       b"\r\n")
print("应用层载荷", len(req), "字节")
print("加传输层首部", len(req) + 20)
print("加网络层首部", len(req) + 40)
print("上线路", len(req) + 58)
```

屏幕上应当是 `84`、`104`、`124`、`142` 四个数。对不上就先看括号里的字节串有没有被编辑器拆错行。

接着把请求行里的 `/index.html` 改成 `/a`，再跑一次。线路上的总字节数少了多少？首部那 $58$ 字节有没有跟着变？

:::

## 分层管不到的地方

分层最实际的好处，是换掉一层时别的层不用动：宿舍的 WiFi 换成网线，只换链路层，IP 地址、端口号、那 84 字节的 HTTP 请求一个字都不用改；HTTP/1.1 换成 HTTP/2，网卡和中间的路由器完全不知道。

分层是设计约定，协议栈里有些功能天生跨越层，最典型的是隧道（VPN）：整个内层 IP 包被塞进外层包的载荷里，于是同一层出现两次首部。把你这条 $84$ 字节的请求塞进一条走 TCP 的隧道，上线路的是 $84 + 20 \times 4 = 164$ 字节，四个首部依次是外层 IP、外层 TCP、内层 IP、内层 TCP，比不隧道时多了 $22$ 字节：

$$20 \times 4 + 84 = 164$$

OSI 七层与实现也不一一对应。会话层、表示层在 TCP/IP 里没有独立的协议，它们要做的事被摊进了应用层与传输层。拿 OSI 的层名去对抓包，只会对不上号。

::: quiz 排错 锚点：隧道里重复的首部
:::

## 记住这三个数

- 四层从上到下：应用、传输、网络、链路；地址依次是域名、端口、IP、MAC
- 封装 = 上层整份当载荷，前面加本层首部；解封装反过来
- 一条 $84$ 字节的 HTTP 请求上线路是 $142$ 字节，其中 $58$ 字节是首部与校验
